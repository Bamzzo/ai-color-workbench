# AI 调色项目：优化空间扫描与开发评估清单

**审查目的：**供开发 Agent 判断哪些后续优化值得实施。本文基于当前工作区源码、项目说明、ADR 与既有测试记录做静态审查；本轮没有修改产品代码，也没有重跑测试或 GUI。历史测试结果只代表对应记录日期和环境，不等于本轮复验。

## 总体判断

项目已经形成较完整的本地调色链路：图像输入归一化、参数化颜色变换、LUT 烘焙、独立 ARM64 渲染 worker、预览与导出、AI 参数提案及测试记录均已具备。已有报告记录 107 项自动测试通过，另有 Mesa/ARM64 worker 自检和一次真实 AI API 调用；这证明了不少核心路径，但不等于完成了发布级验收。

目前最值得优先核对的是**后台任务队列是否会静默丢失导出**，以及**图像像素限制是否在解码前生效**。其次是运行缓存的长期增长、发布/安装路径是否脱离开发机目录、以及人工交互和故障场景验收。参数 v2 与直方图属于功能扩展后的产品体验验证，应通过照片样本和目标用户工作流评估，不能仅凭单元测试认定效果优秀。

## 建议优先级

| 优先级 | 事项 | 当前判断 |
| --- | --- | --- |
| P1，优先核实 | 预览与导出共享 latest-only runner，跨类型排队任务可能互相覆盖 | 有明确代码依据；建议先复现并修正语义或增加回归测试 |
| P1，优先核实 | 图像先 `load()` 再检查像素/边长 | 有明确顺序问题；建议调整为头部检查在前，评估超大图内存风险 |
| P1，验收缺口 | 高 DPI、快速交互、慢 AI 竞争、40MP 峰值、磁盘异常、worker 故障 | 测试记录明确为待人工验收；上线前应补证据 |
| P2，维护性 | Cache 无容量/淘汰策略；旧 job 只在启动时按年龄清理 | 长期使用会积累磁盘占用；需先量实际缓存分布与使用模式 |

## 具体评估项

### 1. 预览与导出任务可能跨类型互相覆盖（P1）

**证据：**`app/jobs.py` 的 `LatestJobRunner` 只保存单个 `_pending`。`submit()` 仅在同 `coalesce_key` 时取消旧任务，但无论 key 是否相同，随后都会执行 `self._pending = spec`。`app/ui.py` 将预览、图片导出和 LUT 导出交给同一个 `self.runner`，对应 key 分别为 `preview`、`export-image`、`export-lut`。因此一个任务正在执行时，如果另一个不同类型任务已排队，新提交会替换它；旧 pending 的取消事件也不一定被置位。

**触发情境：**渲染 worker 忙时用户快速改变参数形成预览排队，随后点击导出；或导出排队后又触发一次预览。被覆盖的导出可能既不执行，也没有对应 `JobOutcome` 让 UI 显示失败。导出对用户意味着明确的持久化操作，不能简单采用“只保留最新”的预览语义。

**建议给 Agent 的任务：**先用一个确定性测试模拟“任务 A 执行中、B 为导出 pending、C 为预览”，确认现状与 UI 提示；再选一种明确策略：将可合并的预览单独调度，导出进入 FIFO 队列/独立 runner，或拒绝并显式提示冲突。需处理同类预览合并、导出不可静默丢弃、关闭时取消，以及 busy 状态和结果归属。

**验收标准：**任意预览/图片导出/LUT 导出交错提交时，用户发起的导出要么执行并报告完成/失败，要么在提交时明确拒绝；不可静默消失。预览仍可按 revision 丢弃过时结果。为交叉 key 覆盖写自动回归测试。

### 2. 图像安全限制在完整解码后才检查（P1）

**证据：**`app/image_io.py::load_source_image` 在 `Image.open()` 后立即调用 `opened.load()`，之后才调用 `_check_container()` 检查格式、帧数、mode、`MAX_SIDE` 和 `MAX_PIXELS`。因此 40MP/16384 限制没有在完整像素解码前拒绝输入；100 MiB 文件字节限制和 Pillow 自带的解压炸弹行为仍在，但不能替代应用自己的尺寸策略。

**影响与边界：**过大压缩图可能在拒绝前占用较多内存和 CPU。实际是否能越过 Pillow 的 warning/error 阈值取决于图像尺寸、Pillow 版本和配置；这里确认的是检查时序不理想，不声称已构成可利用漏洞。

**建议给 Agent 的任务：**确认 Pillow 的 `Image.open` 头部读取可取得尺寸/格式/帧数；先检查允许格式、单帧、mode、边长及像素数，再调用 `load()`。保留 EXIF transpose 后的最终尺寸二次校验（旋转方向会交换长宽），检查截断/损坏文件路径和 `DecompressionBombWarning/Error` 的处理策略，避免全局 warning 策略产生不可预期副作用。

**验收标准：**超限图在完整解码前失败，正常边界图仍能加载；覆盖刚好 40MP、略超 40MP、超单边、EXIF 旋转、坏文件和合法 PNG/JPEG。若实现依赖 Pillow warning 配置，应测试并记录。

### 3. 缓存没有总量限制或淘汰策略（P2）

**证据：**`app/paths.py` 定义 `runtime/cache` 下的 LUT 与 preview 路径；`app/pipeline.py` 另建 `full`、`external` 缓存。写入的 full RGBA 与预览按源图 fingerprint 留存，参数 LUT 按参数 key 留存。启动时 `ui.py` 调用 `cleanup_old_jobs(24)`，该函数只删除超过 24 小时且以 `job-` 开头的 job 目录，不清理上述 cache。当前没有看到缓存最大字节数、按 LRU 淘汰或定期清理机制。

**影响：**反复载入大图、使用不同图片或编辑不同参数后，缓存会持续增长；完整 RGBA 图约为像素数乘 4 字节，40MP 单图约 160MB（未计 PNG 源、临时 worker 输入输出及其他缓存）。运行目录当前统计约 304MB，但里面混有 fixtures、日志、截图和历史 job，不能直接当作 cache 增长的精确基线。

**建议给 Agent 的任务：**先按目录统计 runtime 中 job/cache/log/fixtures 的体积和文件数，确认哪些是开发工件、哪些是产品运行时数据。再评估三类方案：缓存上限与 LRU、启动时按年龄清理、或提供清理入口。清理必须排除正在使用的文件/当前 job，并能容忍文件锁和删除失败；删除缓存只影响性能，不应影响源文件或导出结果。

**验收标准：**在多图和多参数工作流下缓存占用有明确上限或清理规则；正在运行任务所需资源不被删；缓存缺失/损坏后可重建；至少有清理策略的单测或可重复手工步骤。

### 4. 发布与运行路径目前偏向源码工作区（发布门槛）

**证据：**`app/paths.py` 以源码文件位置推导 `ROOT`，runtime 放在应用根目录；`worker_path()` 查找 `build-arm64/Debug`、`build-arm64/Release`、`build/Debug` 或环境变量 `AI_COLOR_WORKER`；worker 命令使用 `paths.SHADER_DIR`。这很适合开发树和本机调试，但源码树是否随安装包携带、安装位置是否可写、shader/worker 如何定位，目前没有发布产物或安装验收记录。基线测试报告也写明“未做发布包”。

**建议给 Agent 的任务：**先明确目标交付物（源码运行、便携包、安装包），再确定资源目录与用户数据目录的分离：worker/shader 作为只读应用资源定位，runtime/cache/log/jobs 写入用户可写位置；环境变量仅作覆盖或调试入口。补充从干净目录启动、路径含空格/中文、非管理员安装、只读应用目录、缺少 worker/shader 的错误提示验证。

**判定：**若暂时只交付给开发者在当前仓库运行，可作为后续发布准备；若准备给普通用户使用，则应列为正式发布阻断项。

### 5. 人工交互与故障验收仍有缺口（上线前必须补齐证据）

**证据：**`docs/test-runs/2026-10-20-baseline.md` 明确标记 T10/T11/T13/T14 部分自动通过，T15 性能验收未完成，并列出高 DPI/指针拖动、坏 DLL/无 GL、只读目录/磁盘满、40MP 与重复编辑 RSS/显存峰值等待验项目。v2 报告另将直方图观感、分离色调页面缩放可读性、预设按钮连点和最小窗口布局列为人工验收。

**优先建议：**

1. 快速调整参数、换图与预览并发时，确认无旧 revision 回跳；导出时继续调整参数，确认导出使用点击时 snapshot，并清楚显示导出的 revision。
2. AI 慢响应期间修改参数或切换文档，确认晚到提案仅作为提案、不覆盖当前编辑；测试取消和窗口关闭。
3. 高 DPI、最小窗口、缩放/平移、A/B 拖动与键盘原图查看；确认控件可读、指针命中位置正确。
4. 40MP 输入以及连续打开多图/重复编辑，记录加载/预览/导出耗时、Python RSS 和 worker 生命周期；报告中区分峰值内存与稳态。
5. 只读输出目录、磁盘空间不足、worker 缺失/启动失败/崩溃/无 GL；确认错误可理解、无半成品、可恢复继续使用。

这些是验收任务，不一定意味着实现缺陷。建议开发 Agent 先按现有功能执行并记录结果，发现失败后再形成代码优化项。

### 6. v2 参数和直方图需要真实照片的产品评审（产品质量）

**证据：**`docs/decisions/ADR-007-params-v2.md` 记录新增字段和兼容规则；`2026-10-20-v2-enhancements.md` 记录 107 项测试通过、LUT 近似数据和一次真实 AI 调用，同时仍要求人工评估直方图观感、分离色调缩放可读性、预设连点、最小窗口比例。测试能够证明参数范围、方向、近似误差和数据结构行为，不能证明照片风格自然或可控。

**建议给 Agent 的任务：**选择一组有代表性的照片（人像肤色、天空/高饱和颜色、夜景、逆光、低对比、透明 PNG），为每个预设和关键参数组合保存基准输出；由人工检查是否出现色偏、断层/剪裁、肤色异常、透明边缘色晕，并记录期望变化。AI 结果采用多个提示语重复调用，评估风格一致性、参数幅度、同义请求稳定性及“保持现状”表达。可将少量典型失败图建立为视觉回归样本，但应允许不同 GPU/Pillow 环境有合理容差。

**边界：**不建议在没有样片或目标审美标准时，仅为了“更优秀”盲目改变颜色公式；这类工作应先形成明确缺陷和可接受结果。

### 7. 关键路径已有较好的基础，避免无依据重构

静态审查也看到一些已有保护：导出图片先拒绝覆盖源文件，PNG/JPEG 通过临时文件原子替换；RGBA 桥验证 magic、stride 和长度；worker 响应核对协议版本、job/document/revision，且输出路径限制在 job 目录；AI 响应有 64KiB 上限、总时限、有限重试、本地 schema 校验和取消检查；AI 日志只记录请求 ID、provider/model、耗时和错误码，不记录用户提示内容；AI 晚到结果按 revision 作为提案保留。可见 `engine_client.py` 和 `ai/deepseek.py` 的这些机制已有相应代码证据。

建议 Agent 将优化聚焦在上面有明确触发路径或验收缺口的事项，不要为了抽象统一而重写这些已具备边界保护的模块。尤其应先补任务队列跨 key 行为测试，再决定调度器改造范围。

## 本轮审查的依据与限制

- 阅读范围包括 `app/image_io.py`、`app/paths.py`、`app/pipeline.py`、`app/jobs.py`、`app/engine_client.py`、`app/ui.py`、`ai/deepseek.py`、`engine/` 协议实现、测试目录、README、ADR 和两份测试记录。

- 本文是静态代码审查加既有记录整理。提交给开发 Agent 时，应让其在当前代码版本复核文件与行号，并先复现标为 P1 的问题，再决定改动。
