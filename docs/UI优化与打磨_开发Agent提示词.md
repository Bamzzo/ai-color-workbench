# AI 调色项目 UI 优化与打磨开发提示词

你现在负责对现有 AI 调色桌面应用进行一次 UI 优化与视觉打磨。请先阅读项目源码、当前测试、`docs/后续开发指导文档.md`、`docs/优化空间扫描与开发评估清单.md` 以及 `docs/test-runs/2026-11-11-ui-manual-acceptance.md`，再开始修改。

本任务的目标是提升现有应用的专业感、信息层级、可读性和操作效率。应用是 Python/Tkinter/ttk 桌面工具，当前核心功能已经可以工作；本次任务以 UI 质量为中心，不要借机重写核心处理链路。

## 一、开始前必须确认

1. 先检查当前工作区是否有其他 Agent 正在运行测试、修改文件或生成构建产物。若发现相关进程仍在运行，先等待其完成，避免在源码处于半修改状态时开始 UI 改造。
2. 阅读真实源码后列出：主窗口入口、主题/样式初始化、主布局、侧栏、预览区、直方图、视频控制、A/B 对比、导出状态、批处理窗口分别位于哪些文件和类中。
3. 记录当前测试基线。已知基线包括：
   - `python -m unittest discover -s tests -q`：204 项通过；
   - `runtime/ui_layout_check.py` 通过；
   - `runtime/batch_mixed_check.py` 通过；
   - `runtime/ui_export_queue_check.py` 通过。
4. 如果当前代码或测试数量已经变化，以实际结果为准，并说明变化原因。不要把旧记录当作当前事实。
5. UI 改造开始前先说明计划修改的文件、界面范围、风险和验证方法。不要直接大范围重构。

## 二、视觉方向

采用“深灰色调色工作台”方向，结合 Codex 的克制、清晰和低装饰感，以及 Adobe、Unity、Unreal 等专业创作软件的深色工作区风格。

具体要求：

- 使用深灰、中灰、浅灰构成中性工作区，不使用纯黑作为大面积背景。
- 预览画面必须是视觉中心，UI 不能用高饱和颜色污染用户对画面色彩的判断。
- 少量强调色只用于当前选中、焦点、进行中、成功、警告、错误等状态。
- 颜色、字号、边距、控件高度、分隔线和圆角应形成统一设计系统，不要逐个控件随意调整。
- 保持整体克制、紧凑、专业，避免大面积装饰、渐变、花哨动画和营销式卡片布局。
- 主要操作应该容易扫描；不让用户为了寻找“打开、预览、调色、导出、批处理”而在多个层级中反复寻找。
- 核心预览区、调色参数、导出状态和批处理队列之间要有明确层级。

## 三、主窗口改造要求

### 1. 总体布局

- 保留现有单素材工作流和功能入口，优先改进布局、比例、间距、颜色和状态反馈。
- 主窗口建议保持“顶部工具栏 + 中央预览区 + 侧栏控制区 + 底部状态区”的工作台结构。
- 中央预览区应获得稳定且足够的空间，窗口缩小时优先压缩预览内容周边的空白，而不是让控件互相覆盖。
- 侧栏内容较多时必须可滚动，滚动条和滚动区域要有明确但不抢眼的视觉表现。
- 侧栏中应区分素材信息、基础调色、曲线/HSL、AI 辅助、视图/对比、视频控制和导出相关区域。可以使用折叠区或分组，但不要把所有内容堆在一个无层次的长面板中。

### 2. 顶部工具栏

- 打开素材、保存/导出、批处理、撤销/重置等常用入口要有稳定位置和明确禁用状态。
- 图标和文字组合应保持一致；仅使用图标的按钮必须有 tooltip 或等价的可访问名称。
- 长文件名不能撑破工具栏。标题、素材名和路径应采用合理截断，并允许通过 tooltip、详情区域或横向滚动查看完整内容。
- 导出进行中时，与切换素材冲突的操作必须体现禁用或阻止状态，不能让用户误以为切换已经成功。

### 3. 预览区

- 预览区域应有稳定边界、清晰背景和适度内边距。
- 原图/效果、A/B 对比、分割线和按住查看原图等现有功能必须保留。
- A/B 状态、分割比例、当前帧和加载状态应以轻量状态信息显示，不遮挡主体画面。
- 加载中、预览失败、无素材和视频帧读取失败等状态必须有明确反馈，不能只留下空白画布。
- 预览更新时避免整个窗口闪烁或布局跳动。

### 4. 调色控制区

- 滑块、数值输入、下拉框、复选框和按钮应统一高度、字体、间距和焦点样式。
- 当前值、默认值、重置入口和修改后的状态要容易区分。
- 重置为默认值必须是明确可见的操作，并且只重置用户能理解的范围；不能误清除素材、导出队列或其他任务状态。
- 不要为了视觉统一而牺牲数值编辑、键盘输入、滚轮调整或焦点切换能力。
- 对参数分组使用清楚的标题和短标签，避免大量解释性长句占据侧栏空间。

### 5. 直方图、视频与对比控制

- 直方图应与预览和调色控制建立清晰关系，不能在小窗口中被底部裁切。
- 视频时间轴、当前时间、总时长和播放/定位操作应保持可见且易操作。
- 时间轴拖动时不能因为状态更新导致控件位置跳动。
- A/B 控制、时间轴和“查看原图”操作在 100%、125%、150% DPI 下都要保持可操作。

### 6. 状态和反馈

至少区分以下状态，不能用一个通用文本相互覆盖：

- 当前预览状态；
- AI 请求状态；
- 当前素材导出状态；
- 批处理队列状态；
- 成功、失败、取消和重试结果。

导出通知至少应能识别素材名、导出类型、结果和输出路径。导出完成后，新一次预览更新不能擦掉仍然有意义的导出结果。错误信息应告诉用户发生了什么以及下一步能做什么，避免只显示异常字符串。

## 四、批处理窗口改造要求

批处理当前已支持混合图像/视频、串行队列、取消、失败后继续、重试以及统一参数/逐项覆盖。UI 改造不得改变这些语义。

### 1. 队列表格

每个队列项至少应能识别：

- 缩略图或视频首帧；
- 素材文件名；
- 媒体类型；
- 尺寸或时长；
- 当前参数策略；
- 任务状态；
- 进度或错误摘要。

列表要适合重复扫描，状态文字和颜色要一致。状态颜色必须同时配合文字，不能只依赖颜色区分。

### 2. 长文件名和长路径

- 长文件名不得把其他列挤出可视区域。
- 列表提供横向滚动能力，确保完整名称和输出信息最终可查看。
- 重要名称被截断时提供 tooltip、详情区或选中后的完整信息。
- 输出路径过长时可显示主体名、末级目录和省略信息，但不能把完整路径永久隐藏。
- 窗口缩小时，优先保证素材列、状态列和操作按钮可用。

### 3. 队列操作

清晰区分“取消当前项”“取消后续任务”“全部取消”“重试失败项”和“移除未开始项”。按钮禁用状态必须跟随队列状态更新。

任务进行中时，批处理窗口应显示当前项、完成数、剩余数和失败数；失败后继续处理下一项的行为要在界面上可观察。不要为了美化而隐藏队列状态或错误原因。

### 4. 策略选择

批次创建时支持三种起始策略：统一参数、逐项微调、参考素材协调。UI 应让用户理解三者区别，但不能把它们做成不可互换的锁定模式。

- 统一参数：应用同一组参数，之后可以对个别素材覆盖。
- 逐项微调：每项独立调整，可以提供复制/粘贴参数。
- 参考素材协调：显示本地分析生成的建议，用户可以预览、接受、重算或恢复；未经确认不能覆盖手动参数。

当前参考素材协调功能若尚未启用，不要伪造一个可用的假入口。可以为未来功能预留合理位置，但必须明确显示为未启用或暂不提供，并避免引导用户以为已经实现。

## 五、响应式、DPI 与可访问性

必须验证以下场景：

1. 主窗口最小尺寸；
2. 批处理窗口约 860×520 的最小尺寸；
3. 125% Windows 显示缩放；
4. 150% Windows 显示缩放；
5. 中文长文件名和长输出路径；
6. 图片、视频以及图片+视频混合批次；
7. 侧栏滚动到最底部；
8. 失败、取消、重试和导出中状态；
9. 键盘 Tab 顺序、Enter/Space 操作、焦点可见性和禁用状态。

要求：

- 字体变大后不能重叠、裁切或导致按钮文字消失。
- 控件宽度、高度和布局不能依赖某一个固定分辨率。
- 窗口缩放过程中不能出现明显布局抖动或控件越界。
- 禁用控件应降低视觉强调，但仍能看出其存在和原因。
- 所有图标按钮应提供可理解的名称或 tooltip。
- 错误、警告、成功和进行中状态不能只通过颜色表达。

## 六、实现约束

1. 先适配现有 Tkinter/ttk 结构，只有在确认当前框架无法满足某项要求时，才提出局部替代方案。不要未经评估迁移到其他 UI 框架。
2. 不重写颜色算法、LUT、渲染协议、图像/视频 I/O、AI API、任务调度、导出快照和队列语义。
3. 不改变“导出未完成时阻止切换素材”的产品规则。
4. 不把串行队列擅自改成并行队列。
5. 不修改 `.env`，不输出 API key、Authorization 头或其他敏感值。
6. 不用大量硬编码坐标解决布局问题。优先使用 grid/pack 权重、最小尺寸、滚动容器、统一样式和可复用布局函数。
7. 不添加与本次 UI 目标无关的依赖、重构或功能。
8. 保留现有测试和运行脚本的兼容性；需要改测试时，只为验证实际 UI 行为而改。

## 七、推荐开发顺序

1. 盘点源码和当前工作区状态，确认没有并行修改冲突。
2. 先建立统一主题变量：窗口背景、面板背景、输入框、边框、主文字、次文字、强调色、成功色、警告色、错误色、禁用色、焦点色。
3. 改造主窗口整体布局和侧栏滚动结构。
4. 改造预览区、工具栏、状态区和导出反馈。
5. 改造批处理窗口的列表、列宽、横向滚动、状态展示和操作区。
6. 完成长文件名、长路径、小窗口和高 DPI 调整。
7. 运行自动化检查并保存关键截图。
8. 人工检查 100%、125%、150% DPI，以及图片、视频、混合批次、导出失败、取消和重试流程。
9. 只有在稳定保存所有源码后再运行完整测试，避免把半修改状态误判为回归。

## 八、验收标准

完成后必须满足：

- 主窗口和批处理窗口形成一致的深灰中性色工作区风格；
- 预览画面仍然是视觉中心，UI 不明显污染色彩判断；
- 常用操作、当前状态和错误原因可以快速扫描；
- 长文件名和长路径不会破坏布局，且可以查看完整信息；
- 最小窗口、侧栏滚动、直方图、A/B、视频时间轴和批处理列表均可用；
- 导出中、成功、失败、取消和重试状态清晰且不会互相覆盖；
- 现有混合批处理、串行队列和导出门控行为保持不变；
- 既有测试全部通过，或对每个失败项给出明确原因；
- 提供改动文件清单、视觉变化说明、测试命令及结果、截图路径和未能验证的项目。

## 九、交付报告格式

请在完成后按以下结构报告：

1. 当前 UI 问题与改动目标；
2. 实际修改的文件和主要改动；
3. 未修改但评估过的部分及原因；
4. 自动化测试结果；
5. 100%/125%/150% DPI 人工验收结果；
6. 主窗口和批处理窗口截图路径；
7. 已知限制、剩余风险和建议的下一步。

不要只报告“界面已优化”或“测试通过”，必须给出可复核的具体证据。
