# AI 调色项目后续开发指导

**用途：**交给开发 Agent 评估并分阶段实现后续 UI 改进与批量处理。本文记录产品规则、功能范围、架构约束和验收标准，不代表功能已经实现或通过测试。

## 1. 当前基线与目标

项目当前以单素材工作流为主：Python/Tk UI 管理一个 `AppState` 和 `document_id`，预览通过可合并任务提交，图片/LUT/视频导出通过 FIFO 提交；渲染由单个后台线程调用独立 worker。静态图片与视频当前帧共用调色、预览和直方图路径，视频整段导出则复用 LUT 并由 ffmpeg 重编码。

后续目标分为两条：

1. 让现有单素材工作流的状态、反馈和交互更清楚，尤其处理导出期间切换素材的歧义。
2. 增加统一的批处理工作区，让用户把图片、视频或混合素材按队列逐项处理，并能选择统一参数、逐项微调或参考素材协调。

本阶段不做渲染并行化。现有目标设备使用软件 OpenGL；多 worker 并发可能增加内存和争用，须先由基准数据证明收益，再另行决策。

## 2. 已确认的产品规则

### 2.1 单素材切换与导出

- 打开新素材后，调色参数、强度、外部 LUT、视图状态及视频时间等按新 document 的默认状态重新初始化。新素材不继承上一素材的调色。
- 若当前素材存在尚未完成的导出（正在执行或排队），阻止加载/切换到另一素材。不要先改变 document 再尝试回滚。
- 在用户选择另一素材后、实际提交加载前检查导出状态；如有导出，给出提示并取消本次切换。建议文案：**“当前素材仍有导出任务正在进行，暂时无法切换。请等待导出完成后再试。”**若有多个任务，可补充剩余数量。
- 该提示是阻止型提示，不提供“仍要切换”绕过选项。当前导出完成或失败后用户可重新发起切换。
- 导出开始时冻结 `RenderSnapshot`。之后界面状态不得改变该任务的源素材、参数、强度、LUT、revision 或目标路径。
- 导出结果通知须能识别所属素材和输出文件。最低限度显示素材名、导出类型、结果路径和 revision；不能只显示一个无法与当前素材区分的“已导出”。
- 导出失败或取消也应归属到对应素材/任务。切换被阻止期间，原素材保持可见且状态一致。

### 2.2 取消

批处理提供两个明确操作：

- **取消当前项：**设置当前任务的取消事件；由图片渲染、ffmpeg 编码等底层路径协作停止，清理临时输出，任务状态标记为“已取消”。
- **取消后续任务：**取消所有尚未开始的队列项，保留当前项继续运行；用户仍可另行点“取消当前项”。
- 如提供“全部取消”，它应明确等同于“取消当前项 + 取消所有排队项”，并在界面上与仅取消排队项区分。
- 取消操作必须幂等；重复点击不产生重复结果、不把已完成任务改成取消，也不留下看似成功的最终文件。
- 关闭应用时按明确的关闭策略处理运行中和排队项；不得静默让用户误以为未执行的项已经导出。关闭确认可概括剩余项数量，并提供继续等待或取消并退出的明确选择。

### 2.3 日志

用户接受在本地日志中记录源路径和目标路径以便排错。日志不得记录 API key、Authorization 头、用户对 AI 的完整描述或图像像素。文档/隐私说明应明确本地日志的保存位置与清理方式；如果日志未来会被打包上传或自动附加到反馈，必须另行征得用户同意。

### 2.4 批处理模式选择

新建批次时，由用户选择一种调色策略：

1. **统一参数：**选择一组参数/预设并应用于所有选中素材；允许之后切换到单项覆盖。
2. **逐项微调：**每项初始独立，用户可逐项编辑参数；可提供复制/粘贴参数作为效率操作，但不应悄悄修改其他项。
3. **参考素材协调：**用户选定一张参考图或视频中的参考帧，其他项根据本地分析生成协调建议。每项建议都能预览、接受、重算或恢复；未经确认不覆盖用户手动参数。

三种策略是批次的起始工作方式，不应成为互斥的锁定模式。用户可以先统一套用，再对个别素材微调；也可以为选中素材生成参考协调建议后，逐项调整。

参考素材协调仅在本机分析素材，不上传图片、缩略图、直方图或路径给 AI/API。它的目标是让一组输出在总体色温、色调倾向和明暗关系上更协调，同时保留素材自身内容、曝光差异和肤色特征；不是把每张图的 RGB/亮度直方图强行变成相同分布，也不是对所有图片复制同一组参数。

## 3. 功能范围

### 3.1 UI 改进（单素材）

- 明确区分素材信息、调色控制、预览/对比、直方图和导出状态；保持当前视觉体系，优先提升扫描、可读性与常用操作效率。
- 统一状态反馈：当前预览、AI 请求、导出任务分别展示状态，不互相覆盖；慢任务需能看到任务类型、目标素材、进度（可用时）和排队数。
- 导出通知保留足够时间，并始终显示导出任务自身信息。新预览完成不能擦除导出中的状态或成功/失败结果。
- 对高 DPI、小窗口、侧栏滚动、视频时间轴、A/B 拖动和键盘查看原图进行人工验收。
- 不以视觉改版为由重写颜色数学、渲染协议或已稳定的图像 I/O。

### 3.2 批处理工作区

首版支持：

- 一次选择多张静态图片、多段视频，或图片与视频混合导入；遵守现有格式/尺寸/色彩限制，逐项显示不支持原因。
- 列表项展示缩略图/首帧、文件名、媒体类型、尺寸/时长、当前策略、任务状态和错误摘要。
- 批次状态至少包含：待处理、准备中、处理中、已完成、失败、已取消、已跳过。
- 用户可移除尚未开始的项、重试失败项、暂停继续（若实现可安全暂停）、取消当前项、取消后续项。
- 选择输出目录、图片格式/质量、视频容器/编码预设（限于现有能力）、命名规则和同名冲突策略。开始执行前预检查目标路径、权限、磁盘空间可用性（若平台支持可靠检测）及源/目标重叠。
- 逐项导出，不把所有源文件一次性展开成大图常驻内存。完成一项后释放其临时资源，再处理下一项。
- 失败项不阻断后续队列项；结果汇总可查看失败原因并重试。

首版暂不包含：多 GPU/多 worker 并行、自动云端处理、复杂时间线/关键帧、批量裁剪编辑、项目云同步、无人确认地覆盖已有文件。

### 3.3 输出与命名

- 默认输出到用户明确选择的目录；禁止覆盖输入源文件。
- 默认文件名应保留原始主体名并增加可识别后缀或按用户模板生成。冲突时提供跳过、改名或覆盖选择；默认不得静默覆盖。
- 图片、视频采用不同的可用格式选项；只呈现当前构建实际支持的格式。
- 每个任务记录输入标识、策略版本、参数快照、参考素材 ID（如有）、输出目标、启动/结束时间、状态和错误码。避免把大型像素数据写进任务记录。
- 任务清单是否跨应用重启保存属于单独决策；若首版不保存，关闭窗口时必须明确提醒未完成项不会在下次自动续跑。

## 4. 建议的实现结构

以下是指导性拆分；Agent 应先核对真实源码和调用关系，再决定具体类名，不要为符合名称而重构。

### 4.1 将批次任务与当前 UI document 分离

当前 `AppState` 是单 document 状态，不应扩展成多个素材状态的杂糅容器。批处理引入独立的批次模型，例如：

- `BatchState`：batch ID、创建时间、全局策略、输出配置、队列状态。
- `BatchItem`：item ID、源素材引用/可重载路径、媒体类型、每项参数覆盖、处理状态、进度、错误与结果。
- `BatchTaskSnapshot`：启动某一项时冻结的源、参数/LUT、强度、视频信息、目标路径和策略版本。

所有 UI 回调使用稳定的 `batch_id` / `item_id` / `token` 关联结果；不能仅依赖列表索引，因为用户可移除和排序项目。

### 4.2 调度器与渲染资源

- 第一版批处理采用单消费者 FIFO，任一时刻最多执行一个重量级渲染/编码任务。
- 预览仍保持 latest-only；批处理导出有不可静默丢弃的任务身份和状态。设计调度优先级时避免持续预览饿死导出，也避免批量队列让用户当前预览长期无响应。
- 需要支持按 item ID 取消当前项和删除/取消后续项，并为所有已接受的任务产生最终状态（完成、失败、取消或明确跳过）。
- 当前 `LatestJobRunner` 的 `cancel(coalesce_key)` 可按 key 取消类别，但批次需要按 item 精确管理；不要用共享 key 代替任务身份。
- 不可让 Tk 控件或 Tk 变量从后台线程访问；worker 线程只产出不可变结果，UI 主线程负责更新界面。
- 首版逐项释放帧、全尺寸 RGBA、LUT 和临时文件；记录单项耗时与峰值内存以决定未来是否试验有限并行。

### 4.3 参数策略

- 统一参数采用不可变基线参数 + 可选 item override；不要在所有 item 间共享一个可变对象。
- 逐项编辑只改变指定 item；“应用到所选项”必须有明确选择范围与可见结果。
- 参数复制/粘贴复制调色参数、强度和必要的 LUT 模式；不复制源路径、预览状态、视频时间、导出状态。
- 外部 LUT 受现有色彩域/叠加限制约束。若一项为外部 LUT 模式，应明确其与参数预设/参考协调的关系，不做隐式叠加。
- 批次开始执行时冻结每项快照；运行中的参数编辑只能影响尚未开始的任务，或要求用户显式重新排队。不得让正在执行的结果悄悄漂移。

### 4.4 参考素材协调

先实现可解释、可测量的本地建议，再评估更复杂算法：

1. 定义协调目标和适用素材范围，至少区分照片/视频 SDR、肤色/自然内容和高饱和场景。
2. 对参考与目标生成稳健的低维统计/特征，避免仅按均值或整体直方图强制匹配；设计保护肤色、黑白点和局部对比的限制。
3. 将差异转换为受参数 schema 约束的建议，设置最大幅度；建议不可表达的目标应显示“不适用/建议有限”，不能伪造精确匹配。
4. 在 UI 中显示参考素材、协调强度/范围与前后预览；用户接受后写入该 item 的参数覆盖，并可恢复原参数。
5. 以多类型素材组做人工盲评/成对评审：人像、风景、夜景、逆光、不同白平衡、混合图片与视频。衡量“组内协调”同时检查单张质量；不以单一数值指标取代观感。

参考协调属于新算法，应单独 ADR 和样片验收，不放在批处理第一版的基础队列完成标准里。第一阶段可先完成“选择模式 + 占位禁用/计划入口”，但不得展示实际可用的虚假功能入口。

## 5. 错误、恢复与安全边界

- 每个 item 的错误需包含可读摘要和稳定错误类别；避免把 traceback 或敏感环境信息直接展示给普通用户。
- 输入在导入时做轻量元数据校验，在执行前再次验证文件仍存在、未变化且仍符合限制；指纹或尺寸变化时要求重新确认/重新载入。
- 导出使用临时文件并在成功后原子替换/提交；失败或取消时清理临时文件，最终目标不得残留不完整内容。
- 同名冲突、只读目录、路径失效、磁盘不足、ffmpeg 不存在/失败、worker 启动失败均需有逐项错误和批次继续策略。
- 缓存清理不得删除当前任务正在读取的路径；批量任务复用现有缓存预算并避免为所有输入预先写出全尺寸缓存。
- 关闭时显示当前项与剩余队列数量；选择“取消并退出”后等待合作式取消和清理达到明确时限。若子进程未退出，提示而非假称完全清理。
- 本地 AI 规则继续遵守 ADR-005：批处理本身不上传图像。若未来提出云端色彩协调，必须另行设计明确同意、数据最小化和隐私说明。

## 6. 分阶段交付建议

### 阶段 A：单素材状态规则与 UI 细化

- 增加“存在运行中/排队导出时禁止切换素材”的门控，覆盖打开按钮、快捷入口以及任何程序化 `load_path` 调用。
- 导出完成/失败/取消通知显示素材标识，避免当前素材与旧任务归属混淆。
- 完成 UI 结构、状态文案和高 DPI/小窗口人工验收。
- 明确导出期间是否允许继续调参；建议允许，导出始终按点击时快照，且新预览状态与导出任务状态分开展示。

### 阶段 B：批处理基础（无参考协调算法）

- 建立批次/item 数据模型、混合媒体导入、顺序 FIFO、逐项进度、失败继续、重试、移除未开始项和取消能力。
- 实现统一参数、逐项微调、复制参数到所选项；开始任务后按 item 快照处理。
- 实现输出预检、冲突处理、逐项结果列表与批次总结。
- 图片和视频各有真实端到端检查；额外覆盖混合队列。

### 阶段 C：参考素材协调

- 先写独立 ADR：目标、算法假设、色彩域、保护条件、适用范围、样片集和评价标准。
- 以离线本地算法生成建议、提供逐项确认与恢复；不影响已完成的基础批处理稳定性。
- 通过人工样片评审后再标为可用，不以单元测试通过替代观感验收。

### 阶段 D：性能和发布评估（另行决定）

- 使用代表性图片/视频测量批量吞吐、内存峰值、取消延迟和稳定性。
- 只有数据表明串行是主要瓶颈且有资源余量，才提出有限并行实验；设定并发上限和自动回退策略。
- 安装包、任务跨重启恢复、项目文件格式等不属于上述阶段的隐含要求，应另立范围。

## 7. 验收标准

### 单素材规则

- 调整素材 A 后打开素材 B，B 的参数/强度/LUT/视图均按默认新文档初始化。
- A 的任一图片/LUT/视频导出正在运行或排队时，尝试切换均被阻止；A 仍保持当前显示，提示文案清晰，任务结束后切换可用。
- 导出结果内容使用提交时快照；完成提示明确关联素材名、revision 和输出路径。
- 取消/失败不会显示成功，不留下最终路径下的半成品。

### 批处理队列

- 可建立仅图片、仅视频、混合媒体批次；不支持/损坏项给出逐项原因，不使 UI 崩溃。
- 同时最多一个重型任务运行；任务顺序与用户选择一致，预览/AI 等交互不会静默移除 batch item。
- 分别验证取消当前项、取消后续项、全部取消、窗口关闭、取消竞态和取消后重新开始。
- 统一参数会作用于批次目标；单项覆盖仅作用于指定项；参考协调的建议须逐项可确认、可恢复。
- 一项失败后其余项按队列继续；失败可重试；已完成项不重复覆盖或重复计数。
- 每项输出与其源、参数快照、文件名/格式对应；同名冲突按用户选择处理，默认不覆盖。
- 多个大图顺序处理时资源可释放，缓存遵守既定上限；长批次测量内存不持续线性增长。

### UI 与可用性

- 高 DPI（至少 125%/150%）、最小支持窗口、侧栏滚动、视频条、A/B 对比、长文件名均可操作且无控件重叠。
- 当前任务、排队数量、已完成/失败/取消数量可快速辨认；进度不会倒退或归属到另一 item。
- 键盘/鼠标焦点、选择多项、批量应用策略和错误详情有清晰反馈。

## 8. 测试建议与副作用

开发 Agent 应在实施前先盘点现有测试写入点，然后增量添加覆盖，不要把历史报告数字当作当前基线。至少包含：

- 批次模型和状态转换的纯逻辑测试；参数基线/单项覆盖及快照冻结测试。
- 调度器 FIFO、取消当前、取消后续、失败继续、结果身份和关闭语义测试。
- 输出命名、冲突、源覆盖保护、临时文件原子提交和失败清理测试。
- 混合媒体真实 worker/ffmpeg 端到端验证及 UI 人工测试清单。
- 真实多图/视频性能测量应独立记录输入条件、总耗时、峰值 RSS、worker/ffmpeg 进程数和失败率。

会写入 runtime、缓存、临时媒体、测试输出或启动进程的验证，应在独立测试目录运行并明确列出清理范围；不要对用户素材做破坏性操作。

## 9. 交给开发 Agent 的执行要求

1. 先复核本文与当前源码；若实现细节不同，报告差异并更新技术方案，不要照抄旧文件/行号。
2. 开始编码前给出拆分后的文件影响面、数据模型、队列状态图、取消语义和测试计划。
3. 按阶段提交；不要把 UI 改版、批处理队列、参考协调算法、并行渲染和安装包绑成一个大改动。
4. 每阶段先实现最小垂直切片，运行相关自动测试和必要端到端测试，记录所有写入目录及结果。
5. 不实现本文件未确认的隐含规则；特别是批次跨重启保存、自动覆盖、云端图像分析和并行 worker，需要单独决策。
6. 最终报告区分代码已实现、自动测试通过、人工验收通过和仍未验证，不以“功能已完成”替代证据。

## 10. 仍需开发时明确的细节

这些不阻止先做阶段 A 或批处理基础设计，但实施到对应界面前应给出默认值或补充决策：

- 队列是否可暂停/继续；首版可不支持暂停，但必须支持取消。
- 批次是否保存到磁盘、是否支持关闭后续跑；首版建议不承诺恢复，关闭时清楚提示。
- “统一参数”应用后，用户修改全局基线时是否传播到所有未开始且未覆盖的 item；建议提供显式“更新未覆盖项”操作。
- 参考协调算法与样片评价标准；在 ADR 和评审完成前不承诺效果。
- 视频参考帧与视频批量输出的命名、音轨保留和编码质量选项，以当前 ffmpeg 能力为准。
- 源文件导入后若发生外部修改，采用重新读取、跳过还是要求用户重新确认；执行前至少应检测并报告变化。
